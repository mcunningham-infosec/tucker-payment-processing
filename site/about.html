About Us

Yes, we know the site is silly at points. A cocker spaniel answers the support questions, a hacker cat attacks the site and a squirrel runs the security operations center. If you think it's silly, you're right, and you're welcome to roll your eyes. But if you made it this far, you were likely entertained enough to want to learn about the real AI technology and enterprise security features behind it. Silly on the surface, serious underneath: here's the serious part.

Tucker Payment Processing is a pretend company with real AI. It exists to show, in a way you can click on, how customer-facing AI should be governed and secured: what each AI is allowed to do, what it is never allowed to do and how every control can be seen working.

There are three AI-driven parts:

  • Tucker, the customer-support agent on the home page, answers policy questions and, once code has verified who you are, questions about that one demo account.
  • Tucker in the store at Tucker's Treats helps shoppers, but can only look things up. Prices and orders are decided by code.
  • The AI SOC in Cipher's Lair is a bounded security analyst. Code-run detection rules wake it while Cipher attacks the site, and it writes the security report live.

How the AI chat and the AI SOC work

Both AIs follow the same pattern: code on both sides, the AI in the middle and the AI never in charge. Each step runs in order.

The AI chat: one message

  1. CloudflareDDoS protection, web application firewall and bot defense. The server accepts web traffic only from Cloudflare.
  2. Apache web serverHTTPS only, strict security headers, size limits and the only door to the app.
  3. Input guardrailsLength and character checks, rate limits and the prompt-injection shield. Blocked messages never reach the AI.
  4. Access decided in codePython decides who you are and which single account you may see. The AI never chooses whose data to read.
  5. AI Chat (Google Gemini)The AI writes the answer, using only read-only lookup tools and the company's own policy documents.
  6. Output guardrailsAnything that looks like a card number or hidden instructions is masked before it leaves.
  7. Behind the ScenesEvery step above is shown to you as it happens, on the home page and in the store.

The AI SOC: one attack run

  1. Cipher attacks100 real attacks against the live site, run from its own server, from web attacks to prompt injection: 50 by hand, then 50 at scanner speed.
  2. Real defenses blockApache, the app's guardrails and the database's own permissions stop each attack, and every one is logged.
  3. Detection rules in code15 blocked attacks from one source wake the AI SOC, a sudden burst is flagged as automated tooling and at 100 code blocks the attacker for 24 hours.
  4. The evidence is boxed inOnly this run's events are passed on: shortened, defanged and marked as untrusted, so attack text can't instruct the AI.
  5. AI SOC (Google Gemini)Reads the timeline, maps it to OWASP and MITRE ATLAS and proposes actions from a fixed menu of three: block, alert or flag a gap.
  6. Python checks everythingActions not on the menu are rejected, every number the AI states is checked against the real events and the block happens whether the AI agrees or not.
  7. Live incident reportThe report is written on screen as the attack runs, and downloads as a PDF.

Each AI is bounded

Tucker

Can: answer policy questions, and look up the one demo account code verified.

Cannot: change anything, see another customer or show more than the last 4 digits of a card.

Tucker in the store

Can: look up products, your cart and your orders from this visit.

Cannot: set a price, give a discount or place, edit or delete an order.

AI SOC

Can: read the run's events and web logs, and write the report.

Cannot: block anyone itself. The block comes from a code rule; the AI only proposes actions, and code checks every number it states.

On top of that: a three-way spending cap on AI costs, your IP address is never sent to the AI and if the AI is unavailable the site falls back to plain facts generated by code instead of failing. And because Cipher's attacks are real, only one attack run is allowed at a time across the whole site. Everyone else waits in a fair, first-come line, using the same queue logic online games use to handle a crowd, except here the attacks are real: you see your place and your wait, and your run starts automatically when it's your turn. It's a hard limit on both AI spending and server load, without turning anyone away.

The technology

Every technology in use on this website is secured to enterprise grade, far beyond what a simple demo site usually has.

  • Google Cloud: a hardened Ubuntu Linux server running Apache, Python (FastAPI) and PostgreSQL.
  • Google Gemini on the paid tier, so conversations are not used to train the model.
  • Cloudflare in front of everything; the server's firewall admits only Cloudflare.
  • Zero-trust admin access: no admin port open to the internet, only Google's identity-checked tunnel with two-factor authentication.
  • Least privilege: read-only database access for the chat, one narrow function for placing orders, no database password to steal.
  • Monitoring: alerts when a defense fails, a spending threshold is crossed or a lockout happens, plus a daily security summary for the owner.
  • Tested: automated tests prove the guardrails hold, and Cipher's 100 live attacks test them again every run.
  • Separate staging environment: every change is built, tested and attacked on its own server, database, secrets and AI budget, behind a Google login, before it reaches this site. Only code moves to production, never test data.
  • Supply-chain and code scanning: every change on GitHub is checked by CodeQL (security flaws in the code), secret scanning (no keys or passwords ever committed) and Dependabot (vulnerable or malicious libraries, with fixes proposed automatically).

Tamper protection

Encryption and strong headers protect visitors on the way to the site. They can't tell you whether the pages themselves were changed. A defaced page or a planted script on a payment company's website is a reputational disaster, so the site's own content is checked continuously.

Every hour, an automated check fetches every page, script and image from the live site, exactly as a visitor receives them, and compares each file byte for byte against the published code on GitHub. Any difference alerts Michael immediately. The check runs outside the server, so an attacker who gets onto the server can't quietly switch it off.

The first run taught a lesson: every page failed. Nothing had been tampered with. Cloudflare, the security service in front of the site, adds two small scripts of its own to each page, one for bot detection and one for analytics. A naive check would raise false alarms forever, and a careless fix ("ignore Cloudflare's scripts") would hand attackers a hiding place. Instead, the check removes Cloudflare's additions only when they match Cloudflare's exact code, down to this site's own analytics ID. Anything that merely looks like Cloudflare's code is treated as tampering. Five kinds of simulated tampering were tested, including a fake script dressed up as Cloudflare's, and all five were caught. Read the code.

Coming next: a second check on the server itself. If it finds a confirmed difference, it takes the site offline behind a maintenance page until the files are restored. It's built to wait out deploys in progress and to never trigger just because GitHub is unreachable. It will run in alert-only mode first, because a security control that takes down a healthy site is its own kind of incident.
